- `apps/api/Dockerfile`'s base image needed `openssl` installed explicitly — without it, Prisma's engine fails with an opaque "Schema engine error" instead of a clear missing-library message. Already fixed in the committed Dockerfile; if you ever strip that `apt-get install openssl` line back out, Prisma will break again with a confusing error.
- The `seed` npm script in `apps/api/package.json` is an intentional stub (prints a message, no-ops) — real seed logic per PRD 14 §5.6 needs the User/ProfessionalClientLink/Exercise models from Phases 3–5 first.
- `apps/api`'s and `apps/web`'s containers each mount a *named Docker volume* over `/repo/node_modules` (`api_node_modules`/`web_node_modules` in `docker-compose.yml`), separate from the host's own `node_modules` at the repo root. This means `@prisma/client` (generated into `node_modules/@prisma/client`) exists in **three independent copies** — host, `api` container, `web`-adjacent tooling — after every schema change. Backend tests (`make test-backend`, or `npx jest` from `apps/api`) run on the **host**, so after any `prisma migrate dev`/`deploy` remember to also run `npx prisma generate` on the host (from `apps/api`) and apply the migration to the `peakform_test` database (`DATABASE_URL=postgresql://peakform:peakform_dev@localhost:5432/peakform_test?schema=public npx prisma migrate deploy`) — the container-side `prisma generate`/`migrate deploy` alone leaves the host stale and host-run tests failing to compile or resolve stale types. **The reverse is just as real and easier to miss**: `docker compose exec api npx prisma migrate dev --name X --skip-generate` (used because the migrations directory is root-owned inside the container, so `migrate dev` must run there, not on the host) applies the migration but — because of `--skip-generate` — does NOT regenerate the container's own `@prisma/client` copy. The running `api` service then throws `TypeError: Cannot read properties of undefined (reading 'findMany')` on every route touching a new model, even though host-run `tsc`/`jest` are completely green (they see the host's regenerated client). Hit this live in the Phase 6 session — the fix is `docker compose exec api npx prisma generate` right after the migration, then confirm via `docker compose logs api` that it recompiled with no `TS2305`/`TS2724` errors before trusting any BDD run against the live stack.
- `apps/api/jest.config.js` uses ts-jest with `isolatedModules: true` (transpile-only, no type-checking) — see §1 above for why. Do **not** flip `apps/api/tsconfig.json`'s own `isolatedModules` to `true` to silence ts-jest's deprecation warning about this: that field also governs the production `tsc`/`nest build`, and NestJS's `emitDecoratorMetadata`-driven DI depends on full type information being available there.

**Implementation notes / deviations from what was scaffolded going in:**

- Playwright's Chromium browser binary had to be installed via `npx playwright install chromium` (without `--with-deps`, since the sandboxed dev environment has no passwordless sudo for the OS-level dependency install) — if BDD scenarios later fail in a fresh environment with a missing-browser error, that's the step to re-run; CI images typically bundle these deps already.

Decisions made while designing it:
  - **`painFlags` is a real relational `PainFlag` table, not a `Json` column**, despite PRD 03 §6 formatting it as "painFlags[]". First implementation used `Json`, but Prisma Client only generates TS types for an enum that's actually used as a field's type — `BodyRegion` wasn't (a `Json` blob doesn't reference it), so `@prisma/client` silently omitted `BodyRegion`/`PainRecency` entirely and every file importing them failed to compile. Fixed by making `PainFlag` its own model (`intakeAssessmentId` FK, `region: BodyRegion`, `severity: Int`, `pastOrCurrent: PainRecency`) — consistent with this codebase's general preference for relational modeling over untyped JSON for structured, safety-critical data (same reasoning as PRD 05's `ContraindicationTag` being a real table, not a string array). `parqAnswers`/`availability`/`equipmentAccess` stay `Json` — genuinely free-form/variable-shape, and PRD 03 §6 explicitly tags them "(JSON)".
  - `MedicalCondition` (enum) and `PainRecency` (enum: `PAST`/`CURRENT`) are new — not in PRD 03 §6's literal field list, needed to give `medicalConditions`/`painFlags.pastOrCurrent` a DB-enforced vocabulary instead of free text, same pattern as PRD 05's `MuscleGroup`/`Equipment`.
  - PAR-Q question codes are **not** a DB enum — they key the `parqAnswers` Json blob and live as a Domain-layer constant (`src/intake/domain/par-q-questions.ts`) instead, so the exact wording/question set (PRD 03 §9's open question, needs PT/physiotherapist review) can be revised without a migration.
  - `medicalConditionsOtherNote` added alongside `medications` — §5.1 requires an "other" free-text field on the conditions checklist that §6's field list didn't itemize (same category of addition as PRD 01's `User.fullName`).

One real bug found and fixed while *verifying* (not just running) this phase against the live stack: a `PATCH /intake/:id` with a partial `parqAnswers` object (e.g. answering one readiness question at a time) was overwriting the **entire** `parqAnswers` Json column instead of merging — Prisma's `update` replaces a Json field wholesale. `POST /intake/:id/complete` then rejected the submission as incomplete even though every question had been answered, just across separate PATCH calls. ## Phase 7 — PRD 06: Training Plan Builder
Full spec: `docs/prds/06-training-plan-builder.md`

### Backend (`apps/api`)
- [x] Prisma schema: `TrainingPlan`, `Mesocycle`, `WeeklyMicrocycleTemplate`, `WeeklyMicrocycleTemplateExercise`, `Session`, `SessionExercise` (§6), migrated (`prd06_training_plan_builder`) and verified against the real Postgres service (host + container clients + `peakform_test`, all three regenerated — see "Known deviations" above). Decisions made while designing it:
  - **No separate `SessionTemplate` entity.** §6 describes `WeeklyMicrocycleTemplate` as "mesocycleId, weekday → sessionTemplate mapping", which reads as if a named, weekday-independent "session template" object exists that a weekday then references (supporting reuse of one named workout across multiple weekdays). v1 skips that indirection: `WeeklyMicrocycleTemplate` (mesocycleId, weekday, name) directly owns its `WeeklyMicrocycleTemplateExercise[]` — one dedicated exercise list per weekday, no cross-weekday reuse. The UI never asked for reuse (the Professional fills out each weekday's session individually), so the extra object would have been unused complexity.
  - `TrainingPlan.clientId`/`professionalId`/`authoredById` — exactly one of `professionalId` (a concrete assignment) or `authoredById` (a Starter Template, §5.8) is set at all times, enforced in the Application layer (`TrainingPlanAccess.assertProfessionalOwnsPlan` checks whichever applies based on `isStarterTemplate` — see the bug below), not a DB constraint.
  - `Mesocycle.order` is server-assigned (`max(order)+1` in `PrismaTrainingPlanRepository.createMesocycle`), never client-supplied — keeps it a gapless total order so `sumWeeksBeforeOrder`/`computeMesocycleStartDate` (pure Domain functions, `src/training-plans/domain/mesocycle-scheduling.ts`, 5 unit-tested cases) never need to reconcile gaps. No `Mesocycle.startDate` column at all — §6's derivation (`trainingPlan.startDate + sum(weeks of lower-order mesocycles)`) is computed at read/generation time, so resizing/reordering an earlier mesocycle shifts every later one automatically.
  - `targetRepsMin`/`targetRepsMax` (two nullable ints, max null = a single fixed rep count) instead of a free-text "reps or rep range" field — stays structured/queryable, same reasoning as PRD 03's `PainFlag` being a real table instead of free-form Json. `targetRpe`/`targetRir` are two separate nullable fields (mutually exclusive, same pattern as `targetLoad`/`targetPercent1RM`) rather than one value + a scale-type enum, since RPE and RIR are different scales (base doc §3.3 — autoregulated prescription).
