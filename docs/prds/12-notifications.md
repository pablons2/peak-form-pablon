## 1. Overview

Cross-cutting notification delivery for the events surfaced elsewhere in the product (missed session, new message, plan updated, etc.). Per [decision 3.2](./00-shared-reference-and-decisions.md#32-platform--responsive-web-only-no-native-app-resolves-base-doc-116), this module scopes channels to **email + optional web push (PWA)** only — no native mobile push is designed for at this stage.

## 2. Goals

- Deliver timely, non-spammy notifications for the trigger events listed in base doc §5.12.
- Support two channels in v1: transactional email (always available) and web push (optional, only if the Client has installed/enabled the PWA and granted permission).
- Respect user notification preferences (which triggers, which channels) without requiring a rebuild of delivery logic per module.

## 3. Non-Goals

- No native push (APNs/FCM via a native shell) — explicitly deferred until/unless a native app is built (base doc §11.6, resolved by decision 3.2).
- No SMS channel in v1.

## 4. Personas & Permissions

Notifications are generated by system events on behalf of a specific recipient user; there's no cross-user notification authoring in this module (a Professional doesn't directly "send a notification" — they send a message, which PRD 11 turns into a notification trigger).

| Action | Admin | Professional | Client |
|---|:---:|:---:|:---:|
| Receive notifications for own account | ✅ | ✅ | ✅ |
| Configure own notification preferences | ✅ | ✅ | ✅ |
| Trigger a notification for another user directly | ❌ | ❌ | ❌ |

## 5. Functional Requirements

### 5.1 Trigger events
Per base doc §5.12 and §3.7, the following events produce a notification for the relevant recipient(s):
- Session reminder (upcoming scheduled session, Client-facing) — sourced from PRD 07.
- Missed session / missed food log (Client-facing, and optionally a digest to the linked Professional) — sourced from PRD 07 / PRD 08.
- New message (Client or Professional-facing, whichever didn't send it) — sourced from PRD 11.
- Plan updated (Client-facing, when a Professional edits an active Training or Nutrition plan) — sourced from PRD 06 / PRD 08.
- Weekly summary ready (Client and Professional-facing) — sourced from PRD 09.
- Check-in due (Client-facing) — sourced from PRD 02 §5.6's `CheckInSchedule`. When a schedule's `nextDueAt` passes, its firing job emits a `CHECK_IN_DUE` domain event that this module's dispatcher (§5.4) turns into a `Notification` exactly like any other trigger — PRD 02 owns *when* a check-in is due, this module owns *how it's delivered*.
- Professional approval decision (Professional-facing) — sourced from PRD 01 §5.6.
- Account security: email verification and password reset (Client- or Professional-facing) — sourced from PRD 01 §5.2/§5.4. Unlike every other trigger above, these are **not** dispatched asynchronously through the `Notification`/`NotificationPreference` flow (§5.4) — PRD 01 calls this module's email-send capability directly and synchronously, because a verification/reset link must go out immediately and can never be delayed, batched, or suppressed by a user preference. They still reuse this module's shared email templates/sending infrastructure (so there's one place that renders and sends transactional email), and they still appear in the in-app notification list (§7) for the user's own record, but there is no `NotificationPreference` row for them and no push-channel variant.

### 5.1.1 Preference-eligible vs. always-synchronous triggers
To avoid ambiguity about which triggers in §5.1 go through the preference/dispatcher path (§5.4) and which don't: every trigger **except** "Account security" is preference-eligible (subject to §5.2's channels and §5.3's per-user toggles). "Account security" is the sole exception, per the note above.

### 5.2 Channels
- **Email (transactional):** always enabled by default for account-critical events (e.g., approval decision) — cannot be fully disabled by the user for these; can be disabled for lower-priority nudges (session reminder, weekly summary). Account security emails (password reset, email verification) are a separate case — see §5.1's "Account security" note — they always send by email and are not subject to this toggle at all.
- **Web push (optional):** only active if the Client/Professional has granted browser push permission in the PWA context. Falls back silently to email-only if push isn't available/granted — no broken experience for users who decline push.

### 5.3 Preferences
- Per-user, per-trigger-type toggle for each available channel (e.g., "missed session" → email on, push on; "weekly summary" → email on, push off), for every **preference-eligible** trigger (§5.1.1).
- Among preference-eligible triggers, "Professional approval decision" is account-critical and not user-disable-able for email. Account security triggers (password reset, email verification) have no preference row at all (§5.1) — not because they're a locked-on preference, but because they never enter the preference system.

### 5.4 Delivery architecture
- All triggers write to a single `Notification` record (base doc §6) regardless of channel, decoupling "what happened" from "how it's delivered" — an Infrastructure-layer notification dispatcher (base doc §7.2) reads user preferences and fans out to the enabled channel(s). This lets new trigger events plug into existing channels without each owning module reimplementing delivery.

## 6. Data Model Additions

Uses base doc §6 `Notification` directly, plus a preferences entity:

- **Notification**: `userId`, `type` (enum of trigger events from §5.1), `payload` (JSON, event-specific context), `readAt` (nullable), `createdAt`.
- **NotificationPreference**: `userId`, `type`, `emailEnabled` (bool), `pushEnabled` (bool) — account-critical types omit the ability to disable email (enforced server-side, not just hidden in UI).

## 7. UX Notes

- In-app notification bell/list is the fallback surface for any event, regardless of channel opt-outs — a user who disables email/push for a trigger still sees it if they open the app (this module isn't just "external delivery," it's also the read model behind PRD 09's unread indicators).

## 8. Out of Scope / Future (Fast-Follow)

- Native push (once/if a native shell is introduced, per base doc §11.6).
- SMS channel.
- Digest bundling (e.g., "3 things happened today" single email instead of 3 separate emails) — v1 sends per-event.

## 9. Open Questions

- None blocking. The "check-in due" scheduling gap noted in earlier drafts of this PRD is resolved by PRD 02 §5.6 (`CheckInSchedule`).

## 10. Acceptance Criteria

- Every trigger event in §5.1 produces exactly one `Notification` record per intended recipient.
- A user who has not granted web push permission still receives account-critical events via email.
- Disabling a non-critical trigger's email/push in preferences stops that channel's delivery for future occurrences without affecting the in-app notification list.
- "Professional approval decision" email delivery cannot be disabled via preferences.
- Password reset and email verification emails are sent immediately regardless of any `NotificationPreference` state (there is none for these types) and regardless of web push permission.
